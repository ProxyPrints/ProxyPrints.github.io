# Self-referential reasoning in the pipeline

As of: 2026-07-29
What this is: a register of every place the card-identification pipeline
**measures itself against itself**, or **consumes its own output as if it
were independent evidence** — and, more usefully, a catalogue of the
recurring _shapes_ those mistakes take, so the next one is recognised
before it ships rather than found by accident.

Reference, not a ruling. This doc records what was found and what was
measured. The decisions several findings need are open GitHub issues,
linked inline and listed under "What needs a ruling". Nothing here has
been fixed by the act of writing it down.

**Read the "Eight shapes" section before writing any new gate, tether,
golden fixture, agreement statistic, or coverage percentage.** That is
the part with a shelf life. The findings register below it is the
evidence the shapes are real.

## Why this doc exists

Seven instances of self-referential reasoning had each been found _by
accident_, one at a time, in the course of unrelated work. That is a bad
way to find a class of defect. The owner asked whether the seven were
everything, and a deliberate read-only audit was commissioned to answer
it.

The answer is no. **Twenty further instances** were found: nine where the
measurement _cannot return a different answer_, and eleven where it can
but the sample is selected in a way that biases it. Five things that look
circular were checked and are provably sound; they are recorded here too,
so nobody re-litigates them.

The point of writing this up as reference rather than as a dated report
is that a defect class found seven times by accident and twenty times on
purpose is not a historical event. It is a standing hazard in how this
project writes measurements.

### The number that frames everything below

Of **230,770** Cards, exactly **4** are `resolved` and **22** are
`no_match`. **230,744** are `unresolved`. There are **167,229** printing
votes, of which **125 (0.075%)** are human.

Any measurement gated on a resolution outcome is therefore measuring a
population of four. Several are. This is not itself a defect — it is the
correct consequence of the human-backed gate that
[`../theory.md`](../theory.md) is built around — but it means a check
that reports "0 problems found" is, today, usually reporting "nothing was
examined". Those two statements must never be allowed to look alike.

## Eight shapes

Six of these were named in the commission; two more fell out of the
findings. Each is stated as a smell you can check a diff against.

### 1. A "ground truth" fixture recorded from the thing it grades

The fixture is generated by running the extractor, then saved as the
extractor's expected output. It can detect a **changed** extractor. It
can never detect a **wrong** one — and because it pins the extractor's
errors as expectations, its only possible operational effect is to
_resist correction_.

The tell: the fixture's own comments say where the values came from, and
the answer is "a real run of the code under test". A second tell is a
commit that changes an implementation and edits the expectation in the
same diff. Ground truth does not move when code moves; **a lock that is
unlocked to admit the change is not a lock.**

Instances: `C1` (the golden set), `C8` (`BORDER_COLOR_TO_TAG`), `C9`
(`test_skip_reason_roster.py`).

### 2. A gate whose uncomputable criteria are dropped rather than failing it

A criterion that cannot be evaluated returns "unknown", and the aggregate
verdict filters the unknowns out before deciding. The gate then cannot
distinguish **"the run was clean"** from **"the run did not happen"** —
and the second is precisely the failure the gate exists to catch.

The tell is an aggregate of the form `all(x for x in items if x is not None)`, or any report whose empty-set case prints a pass.

The repo already contains the right answer to this, in
`scripts/ops/crash_drill.sh`, which exits non-zero with "DRILL-FAIL:
nothing provable this pass" when it could not prove anything. Same
situation, opposite choice.

Instances: `C2` (the soak gate, proven by execution), `C5` (the cluster
contradiction detector, vacuous rather than broken), and the "Gate check
passed: 0/N" family in `K11`.

### 3. An eligibility filter that removes rows from a population another calculator COUNTS

This is the subtle one, and it is the shape that defeats a control.

A cohort of votes can be held at **zero consensus weight** and still
change outcomes, because a calculator's `_eligible_base_queryset` excludes
cards that already carry a vote — from _any_ identity, at any weight. The
excluded rows never touch the weight arithmetic. They still vanish from a
population some other calculator takes a `COUNT` over, and that count is
the premise of an inference.

The tell: a queryset used as a denominator, a frequency, or a uniqueness
test, whose filters mention votes, scan-log rows, or statuses that the
pipeline itself writes. Weight-neutrality is not influence-neutrality.

Instances: `K1` (name-frequency elimination — 3,450 spurious singleton
names, 100% attributable to one exclusion), `K2` (the "what could this
cover" report, off by ~2x).

### 4. An agreement rate between two channels that share a decoder

Two identities agree at 99–100%, and this is read as corroboration. It is
not, if one channel is the other's decode plus extra layers: **a pair
that cannot disagree cannot corroborate.**

Two tells, both stronger than the agreement rate itself:

- **Shared constants.** One channel reads the other's crop box, regexes,
  normaliser, or candidate index.
- **One-directional disagreement.** If channel A abstains where B commits
  but B never abstains where A commits, that is the signature of a strict
  subset, not of an independent method. One-directional containment is
  better evidence of non-independence than any agreement rate is of
  independence.

Watch also for agreement that is _manufactured by suppression_: if a
disagreement between two engines causes **neither** vote to be cast, the
surviving population is agreement by construction, and the observed rate
is necessarily 100%.

Instances: `F6` (the audit's own corrected false alarm — see below),
`K11` (`ocr_engine_ab`), and the fidelity gate's 83.2% headline,
documented separately in the companion audit (PR #586).

### 5. A test whose fixture is built from the constant the implementation reads

The test iterates a mapping to construct its input, then asserts the
result equals that same mapping's value — while the implementation _is_ a
lookup in that mapping. The assertion reduces to `d[k] == d[k]`. It
passes for every possible content of `d`, including wrong content.

The tell: the fixture and the expectation are derived from the same
symbol, or the test parametrises over a hand-written literal that sits in
the test file rather than over the implementation's own declaration.

The check that catches this is the mutation question, and it is worth
asking in review of every new test: **is there a single-line change to
the implementation that would redden this?** If not, the test is
documentation.

Instances: `C8` (a wrong colour-to-tag mapping would mislabel 138,728
cards with every test green), `C7` (the implicit-vote cap is dead code
under all five of its own tests), `C9`, and the D1 exclusion test in
`C3`, whose fixture is a state the real importer cannot produce.

### 6. A doc tether that checks a string APPEARS rather than that the claim is TRUE

`re.search(identity, prose)` verifies that a calculator is _mentioned in
a document_. It does not verify that the mention is accurate, and it does
not verify that the calculator does anything. Making the **mention**
mandatory while leaving the **accuracy** unchecked produces a green
tether over a channel that has never cast a vote.

The tell is any lint whose success condition is substring presence.
Related: a check that does not strip fenced code blocks will accept a
filename inside a code fence as a satisfied cross-reference.

Instances: `C9`. This shape is already the subject of issue
[#577](https://github.com/ProxyPrints/ProxyPrints.github.io/issues/577),
which proposes the fix: make the roster entry a machine-readable contract
and check it against production, adding a doc-to-reality direction to the
existing code-to-doc tethers.

### 7. A denominator that is the run's own output

"Gate check passed: 0/N violations" reads as a catalogue-wide assurance.
It is not, when `N` is the number of rows _this run just wrote_. A
violation created by an earlier run is permanently invisible to every
later gate, because no later run's denominator ever contains it.

The tell: the gate's population is scoped to `run_id`. One site in the
repo (`MPCAutofill/cardpicker/deductive_backfill.py`) has the population
precondition that makes the phrasing sound; eight copies inherited the
words without the guarantee.

Instance: `K11`.

### 8. A stored field that reads as a fact about the world but is a fact about our own completeness

A column named as though it describes reality — "how many printings
exist" — is computed as a count over our own rows: "how many rows our
importer landed". Those two differ **precisely when the import is
incomplete**, which is the only case any consumer cares about. The field
cannot detect its own failure mode, and any gate built on it inherits
that blindness.

The tell: a denormalised counter with no external source, especially one
whose fallback branch asserts a fact (`else 1`).

Instance: `C4`, and `C3`, the gate that depends on it.

## Findings register

Identifiers are the audit's own, kept so that this doc, the issues, and

### CIRCULAR — the measurement cannot return a different answer

#### C1 — The golden set is the extractor's own output, and no extractor is ever run against it

LIVE as a claim, LATENT as a mechanism.
`MPCAutofill/cardpicker/golden_set.py` (665 lines),
`MPCAutofill/cardpicker/tests/test_golden_set.py` (172 lines).

The module calls its contents "Per-card ground truth" and calls the file
"the literal hard gate task #145 requires", stating that "each
extractor's own test file imports `get_golden_cards()` ... and checks
against whatever key it owns in `GOLDEN_EXPECTATIONS`".

Six findings, each independently sufficient:

1. **Every expectation was recorded from the extractor it grades.** All
   ten blocks say so in their own comments — "recorded 2026-07-19 against
   a real `extract_card_evidence()` run", "`value` is
   `classify_border_color`'s own output". There is no external oracle in
   the file: no human label, no Scryfall field, no `Card.canonical_card`.
   It is a characterisation snapshot wearing the word "truth".
2. **No extractor test consumes it.** A repo-wide grep for
   `GOLDEN_EXPECTATIONS` / `GOLDEN_CARD_IDS` / `get_golden_cards` returns
   the definition, its own test file, and six prose comments. Nothing
   else.
3. **All 26 assertions in its only test file are type/membership checks
   over hand-typed literals** — e.g. `assert all(e.value in ("bleed", "trimmed") ...)` over a literal dict, while the implementation is
   literally `return "bleed" if dist_to_bleed < dist_to_trim else "trimmed"`. Analytic mutation: stub `extract_card_evidence` to return
   `None`, make `compute_card_art_hash` return 0, delete
   `_PROXY_MARKER_RE`, force `classify_bleed_edge` to return "trimmed" —
   every test in the file still passes. There is no single-line
   implementation change that reddens it.
4. **The only DB-touching golden test asserts the gate is inoperable.**
   It asserts that `get_golden_cards()` _raises_, because the pinned
   production pks never exist in the test DB. If anyone ever seeded them,
   that test would fail.
5. **The pins are not true.** Of the 13 non-blank `set_code` values
   pinned as the expected `collector_line_ocr` answer, **9 are not real
   MTG set codes** — measured against the 1,047-row canonical expansion
   table: `foe`, `mtg` (x3), `oey`, `thato`, `ahr`, `proxy`, `cls` are
   absent; only `j25`, `sld`, `dmr`, `msh` exist. "mtg"/"2024" is a
   copyright line misread as a set code plus collector number, and it is
   pinned as correct.
6. **The pin moves to match the code.** Commit `52a51e9f` (2026-07-23)
   widened `_PROXY_MARKER_RE` and, in the same commit, edited card
   208337's expectation from `False` to `True`. The file's own comment
   says `False` "was the correct output of the OLD ... regex, but is no
   longer what the current parser produces".

Honest version: label it a regression snapshot, or rebuild it with
external labels — free for the 10,337 cards whose `Card.canonical_card`
is non-null, where Scryfall's own `set_code`/`collector_number`/`artist`
were never produced by this pipeline. Until one of those happens, **no
accuracy claim may rest on "the golden set passes"**, and the nine
fabricated set codes must not be treated as expected values. Needs a
ruling — see "What needs a ruling".

#### C2 — The soak gate returns PASS for a run that never existed

LIVE. This is the documented Stage E widen/halt decision
([`../soak-gate.md`](../soak-gate.md)).
`MPCAutofill/cardpicker/soak_gate.py`:

```python
return all(c.passed is True for c in self.criteria if c.passed is not None)
```

A criterion that **cannot be computed** returns `passed=None` and is
dropped from the verdict rather than failing it. The real evaluator was
run, read-only, against a `run_id` that has never existed:

```
OVERALL all_passed = True
  fetch-failure-rate            passed=None   0/0
  unacknowledged-envelope-trips passed=True   0 open trip(s)
  evidence-cohort-count         passed=None   cohort_size unknown
  zero-machine-resolutions      passed=True   0 voted cards
  ledger-heartbeat              passed=True   no ledger row
  vote-yield                    passed=None   no ledger row
```

`MPCAutofill/cardpicker/management/commands/soak_gate_report.py` then
prints `VERDICT: PASS — safe to widen to the next step` and exits 0.

Three compounding defects, each verified in code:

- **Criterion 3 is the only one comparing output against an intended
  cohort**, and its reference is `PilotRunLedger.counters["cohort_size"]`
  — a number the graded run wrote _about itself_, after `_run_cohort`
  returns. A run that died mid-cohort (the exact failure the criterion
  exists to catch) has no `cohort_size`, so it abstains, and the
  abstention is dropped. Measured: only **16 of 995** `PilotRunLedger`
  rows carry that key. The criterion is uncomputable for **97.9%** of
  runs.
- **Criterion 4 ("zero cards resolved by machine votes alone") cannot
  fail for the reason it names** — `MPCAutofill/cardpicker/vote_consensus.py`
  makes a machine-only group unresolvable by construction. It _can_ fire
  in the wrong direction: it takes every card the run touched, including
  cards already carrying human votes, for which `resolve_printing`
  correctly returns a printing, and then recommends
  `purge_machine_votes --run-id <id>`.
- **Criterion 5 returns `passed=True` for a FAILED ledger row**, and the
  module header still advertises a heartbeat check ("no gap > 1h between
  `PilotRunLedger` activity timestamps") that is unimplementable because
  `run_id` is unique. A weaker check was silently substituted.

Honest version: make `passed is None` block a PASS; capture
`cohort_size` before the cohort runs; scope criterion 4 to cards with no
pre-existing human vote. The first of those changes Stage E widen/halt
semantics and needs a ruling, not a patch.

#### C3 — The D1 "cross-verified against Scryfall" gate has never excluded anything and structurally cannot

LIVE. `MPCAutofill/cardpicker/deductive_backfill.py`.

The comment states the D1 rule is "name matches exactly one
`CanonicalCard`, cross-verified against Scryfall's own `printings_count`
(not just 'our table happens to have one row')". The gate is
`if len(matches) == 1:` then `if printings_count == 1:`.

But `printings_count` **is** "our table happens to have N rows" — see
`C4`. Test 1 is "one row with this name"; test 2 is "one row with this
oracle id"; rows sharing an oracle id share a name, so test 1 implies
test 2.

Measured: of the **14,940** `CanonicalCard`s whose name is unique in the
table, **14,940** have `printings_count == 1`; 0 have >1, 0 have 0, 0
lack a sidecar. **The second conjunct has rejected zero candidates in its
lifetime.**

The test that pins the intended behaviour —
`MPCAutofill/cardpicker/tests/test_deductive_backfill.py`'s
`test_printings_count_greater_than_one_excludes_from_d1`, whose comment
reads "printings_count says there are more real printings we haven't
imported yet" — builds a fixture with one name row **and**
`printings_count=2`, a state the real importer cannot produce. That is
why this survived review; it is shape 5.

Live consequence: the 2026-07-29 re-scoping restored ordinary machine
weight to future deductive-backfill runs, so the next run casts weighted
votes behind a check that does nothing.

#### C4 — `printings_count` is a counter over our own rows, and its docs are false

LIVE. `MPCAutofill/cardpicker/printing_metadata_import.py`.

Measured: stored column vs a live `COUNT(*) GROUP BY canonical_id` over
`cardpicker_canonicalcard` — **113,143 agree, 0 disagree**. It is a pure
denormalisation of our own row count, everywhere. Nothing from the
Scryfall bulk file contributes; the `else 1` branch asserts that a row
with a null oracle id has exactly one printing in existence.

`docs/features/printing-tags.md` lists it among "the Scryfall fields
`CanonicalCard` doesn't hold" and repeats the D1 cross-verification
claim. **Both sentences are false as written.**

Related and confirmed: **there is no import timestamp anywhere.**
Verified against `MPCAutofill/cardpicker/models.py` and against
`information_schema` — the four canonical tables and `cardpicker_card`
carry no `created_at`/`updated_at`/`imported_at`; the only date column is
`released_at`, Scryfall's card release date. The staleness of the
reference frame is unknowable from the database.

#### C5 — The "free contradiction detector" checks zero clusters

LIVE, vacuous. `MPCAutofill/cardpicker/local_cluster_consistency.py`.

Billed in its module docstring as [`../theory.md`](../theory.md) §6's
contradiction detector and as "the federation export's pre-flight audit".
It groups by `content_phash` over cards filtered
`printing_tag_status=RESOLVED` **and**
`inferred_canonical_card__isnull=False` — both pipeline-written
conclusions.

Measured by running its exact query: `clusters_2plus = 0`, `divergent = 0`. With four resolved cards catalogue-wide, no cluster of 2+ resolved
members exists. The command prints "no divergent clusters found", which
is indistinguishable from "nothing was examined" — shape 2.

In fairness: **the check is sound in principle** and can fire once
resolutions scale, because the calculators are deterministic on identical
pixels, so only two disagreeing _humans_ could produce a divergence.
Classify it vacuous-now, not broken. But it must never be cited as
evidence of consistency.

#### C6 — `get_funnel_counts`'s "confirmed" asks whether the machine agrees with a conclusion its own vote elected

LIVE, tiny. `MPCAutofill/cardpicker/views.py`.

The numerator requires `RESOLVED` + non-null `inferred_canonical_card` +
an `Exists()` machine vote for that same printing. But
`inferred_canonical_card` is `resolve_printing`'s output and the machine
vote is one of its inputs, sitting inside the winning group by
construction. It can only come out `False` when humans overrode the
machine outright — and per `K3` those humans were shown the machine's
answer. Measured: **1 confirmed of 4 resolved**.

#### C7 — The implicit-vote cap is dead code under every test in the suite

LIVE. `MPCAutofill/cardpicker/tests/test_vote_consensus.py` vs
`MPCAutofill/cardpicker/vote_consensus.py`.

All five tests in `TestImplicitVoteCapForm` — including one named
`test_implicit_weight_is_hard_capped_per_outcome_group` — place two human
votes (weight 1.0) on the winning side, which sets `exclude_non_human = True` and drops all non-human weight **before** `full_weight()` (the
cap's only call site) is ever reached.

Analytic mutation: delete the `min(...)` from `vote_consensus.py`. Every
test stays green. `PRINTING_TAG_IMPLICIT_CAP` appears in exactly two
files repo-wide, so nothing else can catch it. This guards the "machine
volume cannot resolve alone" invariant the project is built around.

#### C8 — `BORDER_COLOR_TO_TAG`'s values are asserted against themselves

LIVE. `MPCAutofill/cardpicker/tests/test_local_layout_class_cast.py`,
`MPCAutofill/cardpicker/tests/test_local_fallback.py`.

The test iterates the dict to build the fixture and asserts the verdict
equals the same dict's value; the implementation _is_
`BORDER_COLOR_TO_TAG.get(...)`.

Analytic mutation: set `"black": "White Border"` in
`MPCAutofill/cardpicker/local_fallback.py` — all tests in both files
pass, and every black-bordered card in the catalogue (**138,728 rows**)
is voted "White Border". A sibling test named
`test_every_taxonomy_color_maps_to_a_real_tag_name` asserts only the
**key** set; nothing anywhere asserts the values are real `Tag` names.

#### C9 — Three mutation-proof tests in the most recent PR, and two mention-only doc tethers

LIVE (the first is `origin/master` only).

`MPCAutofill/cardpicker/tests/test_skip_reason_roster.py` parametrises
over the **hand-written** `EXPECTED_SKIP_REASONS` dict 40 lines above it,
not over `_declared()`, and asserts those literals are non-empty and
stripped. No implementation change can fail it. A second case is strictly
subsumed by a third (dict equality implies key-set equality) yet counts
as separate coverage.

`.github/scripts/docs_lint.py` — the roster tethers for calculators and
for skip reasons are `re.search(identity, prose)`: they verify **a string
appears in a doc**, never that the doc's claim is true. Confirmed
concretely: `local-name-frequency-v1` is declared, appears in
`docs/pipeline-fidelity-gate.md`, the tether is green, and the calculator
**has cast zero votes ever**. The soft supersession and
proposal-cross-reference checks are also mention-only; the latter does
not strip fenced blocks, so a filename inside a code fence satisfies a
cross-reference requirement.

And the roster's completeness claim is false: three bare inline literals
bypass the `*_SKIP_REASON` convention the derivation scans —
`"no-evidence"`, `"eliminated"`, `"ambiguous"`, all in
`MPCAutofill/cardpicker/local_fallback.py`.

Issue [#577](https://github.com/ProxyPrints/ProxyPrints.github.io/issues/577)
already owns the calculator-roster half of this. The skip-reason tether,
the two soft checks, and the three bypassing literals are recorded there
as an extension rather than as a duplicate issue.

### CONTAMINATED — it can return a different answer, but the sample is biased

#### K1 — Name-frequency elimination deduces from the residue, and the zero-weight control is what creates the false premise

LATENT BUT ARMED.
`MPCAutofill/cardpicker/local_identify_printing_tags.py`.

The gate casts a vote naming a specific printing when there is "exactly
one uncovered printing AND exactly one unresolved-eligible card". Its own
docstring calls the second conjunct "the difference between a sound
inference and a coin flip".

But the count is taken over `_eligible_base_queryset`, which first
removes cards carrying this identity's own votes, cards carrying a
`deductive-backfill-v1` vote, cards with a non-rescannable scan-log row,
and tag-excluded cards.

Measured two independent ways, agreeing on the shape:

| pool                                                         | singleton names |
| ------------------------------------------------------------ | --------------- |
| names singleton in the eligible (residue) pool               | 71,391          |
| names singleton in the honest pool                           | 77,885          |
| **spurious** — singleton ONLY because siblings were excluded | **3,450**       |

A second, narrower simulation restricted to names that _also_ have
exactly one uncovered printing (i.e. names on which the gate actually
fires) found **2,708 firings, of which 133 (4.9%) rest on a false
premise, hiding 344 unresolved cards.** Both methods attribute **100% of
the cause to the deductive-backfill exclusion**;
`local-name-frequency-v1` itself has zero votes and zero scan-log rows.

The sharpest form: the 28,112-vote deductive-backfill cohort was zeroed
to weight 0.0 expressly so it could be "a measurement control held
permanently outside the resolution math ... **without the control's own
votes having influenced the thing being measured**"
(`MPCAutofill/cardpicker/vote_consensus.py`). **It is not outside.** It
never touches the weight arithmetic, but its mere presence deletes rows
from a population another calculator `COUNT`s, and thereby changes what
that calculator concludes. Influence via the eligibility filter, not via
weight. This is shape 3, and it needs a ruling.

#### K2 — "How many cards could deductive backfill cover?" is off by 2x, and the 2026-07-29 re-scoping may be a no-op

LIVE for any published number.
`MPCAutofill/cardpicker/deductive_backfill.py` (byte-identical in
production).

Measured: population the method's non-vote preconditions admit =
**204,339**; eligible today (`printing_tags__isnull=True`) = **104,969**;
removed because _something_ already voted = **99,370**. Only **28,112**
of those are its own votes; the rest were removed by sibling machine
calculators whose votes can never resolve anything either. The protective
scenario the exclusion was written for requires a pre-existing **human**
vote — and there are 125 human votes on 100 distinct cards.

So the guard is doing ~100 cards of intended work and ~99,270 cards of
unintended self-and-sibling exclusion, and `--dry-run` (the "what could
this cover" report) prints the residue.

Consequence worth a ruling: **every card in the frozen zero-weight cohort
carries `printing_tags` and is therefore permanently ineligible for a
re-run.** The method can never re-cover the exact cohort whose votes were
zeroed, so the ruling that restored weight to future runs may have no
reachable population.

#### K3 — Machine output selects and pre-answers the human questions that are the only thing that can resolve a card

LIVE. `MPCAutofill/cardpicker/question_feed.py`.

1. **A zero-weight vote still buys the outcome.**
   `_confirm_suggestion_item` selects any DEDUCTION/OCR vote with **no
   weight check and no `run_id` exclusion**, so a vote from the 0.0-weight
   control cohort is rendered to the human as `suggestedPrinting` — the
   answer to confirm — and returns as a full-weight USER vote that does
   count. Measured: **8,216** cards have `deductive-backfill-v1` as their
   **only** machine identity; **8,207** are tier-1-eligible right now. The
   control determines outcomes one click downstream, on ~8.2k cards.
2. **Contested cards are shown as confident ones.** Tier 1 has no
   distinct-outcome check and is consulted before the "contested" tier,
   and the displayed suggestion is chosen by **lowest pk** (an unordered
   `.first()`) — not weight, not agreement. Measured: **1,889** cards
   carry ≥2 distinct machine outcomes today.
3. **≥51% of questions are drawn from cards the machine is one vote from
   winning** (`is_likely_resolve_printing`, ratio default 0.51). This is
   owner-ratified and instrumented — every served item is logged to
   `QuestionFeedServedLog` as, in the module's own words, "the
   bias-conditioning record". The hook exists; **it has never been used.**
   Any "humans agree with the machine X%" statistic is computed over a
   population the machine chose, on items where it supplied the default
   answer.

#### K4 — The engine's own failure record decides what it is allowed to try next, and the cap closes the loop

LATENT (the command last ran 2026-07-16).
`MPCAutofill/cardpicker/local_identify_printing_tags.py`.

A name is "proven hard" for an engine when **that engine** has ≥5
non-rescannable scan-log rows for it and **zero votes** for it, all-time.
Hard names sort to the back of the queue. The docstring defends this as
"Demotion, not exclusion ... never permanently lost the way a hard
exclusion would be".

That defence does not survive the cap. `--limit` defaults to **300** per
engine per invocation and the queue is sliced `[:limit]`.

Measured: `local-ocr-v1` has **1,274** hard names covering **10,295**
cards; `local-phash-v1` has **4,710** hard names covering **48,201**
cards — **20.9% of the catalogue** demoted behind a non-demoted pool of
~182k cards, against a 300-card cap. A demoted name is never reached, so
it never gets the one vote that would rescue it, so it stays demoted.
Self-fulfilling in operation.

The same interaction makes any per-run yield figure a figure about a
coverage-and-success-selected sample, never about the catalogue.

#### K5 — An artist check that is tautological for 79.4% of names — lands on the next deploy

**LATENT in production (85d88bfe), LIVE in `origin/master`.**
`MPCAutofill/cardpicker/image_evidence.py`,
`MPCAutofill/cardpicker/collector_line_artist.py`,
`MPCAutofill/cardpicker/local_calculate_verdicts.py`.

illustrated a printing of this card's name** (via the same
`CandidateNameIndex` Stage D uses), and `canonical_name` is set only when
that narrowed set has exactly one member. Stage D then treats agreement
between that stored name and the matched printing's artist as
corroboration, downgrading confidence on disagreement.

Measured: **28,231 of 35,569 canonical names (79.4%) have exactly one
distinct artist.** For those, the recovered name is _forced_ to equal the
matched printing's artist and
`JOIN_KEY_CONFIDENCE_ARTIST_DISAGREEMENT` is unreachable.

Honest note: the module's own defence ("it is NOT circular") is
**correct** for the veto consumer it discusses — narrowing there is
outcome-neutral. It simply does not extend to the **storage** path, which
is where narrowing is decisive and which feeds the corroboration check.

#### K6 — Evidence-transfer rows dilute the fetch-failure gate

LIVE, not yet decisive. `MPCAutofill/cardpicker/soak_gate.py`,
`MPCAutofill/cardpicker/evidence_transfer.py`.

Measured: 220,669 evidence rows, 7,869 transferred (3.57%), 1,603 fetch

#### K8 — The pipeline's own conclusion re-enters as fresh evidence under a new agent identity

**Partially narrowed for printing votes, 2026-08-05 (issue #661/PR
#695).** The asymmetry above is unchanged for artist evidence (this

see [`../identification-pipeline.md`'s "Stage C+"
section](../identification-pipeline.md#stage-c--the-md5-group-behaves-as-one-unit)).
It has narrowed specifically for printing-vote **pooling** itself:
`printing_consensus.py`'s identity group

enforced on — remains true pipeline-wide, artist consensus included.

#### K10 — Resolution hides a card from every surface that could correct it

### FINE — looks circular, is not

Recorded with the code that proves it, because a false alarm reported
honestly is worth more than a silent one. **Do not re-litigate these
without new evidence.**

#### F1 — The confidence invariant holds, more strongly than its docstring claims

`resolve_vote_weight(source, anonymous_id, run_id)` takes no `confidence`
argument, and its docstring forbids adding one. All 178 `confidence`
occurrences and all 19 attribute reads were traced: **every read is on an
in-memory verdict dataclass in the same process that computed it**, at
the moment the row is constructed. **The persisted column is write-only**
— no `.filter(confidence)`, no `.order_by("confidence")`, no aggregate,
anywhere. Its only consumer is Django admin `list_display`. There is no
leak into weight, tie-break, ordering, winner selection, gate, queue
sort, or any consensus-facing metric.

The punchline vindicates it concretely: `deductive-backfill-v1` — pure
name matching, zero image inspection, the cohort deliberately zeroed to
weight 0.0 — asserts the **highest** confidence in the database
(0.90–0.95), above every image-inspecting channel. Had confidence ever
scaled weight, the least evidentially-grounded channel would have bought
the most influence.

(Confidence values are hardcoded per-calculator tier labels, 1–4 distinct
values per identity, on no common scale, with no calibration anywhere —
which is fine precisely because nothing compares them.)

#### F2 — The version-bump quorum bug is genuinely closed

`agent_dedupe_key` (`MPCAutofill/cardpicker/printing_consensus.py`) keys
pooling on the versionless calculator **family**, and `pool_group_votes`
is only reached when the md5 group has >1 member — which leaves
**196,675 of 230,770 cards (85.2%)** as md5 singletons with
`dedupe_key=None` and no pooling at all. That looks like a large
unguarded surface, since the uniqueness constraint is `(card, printing, anonymous_id)` and would happily hold a v1 and a v2 row on one card.

**It is guarded elsewhere:** `models.purge_stale_machine_votes` deletes
every row of the same family, any version, for the targets a calculator
is about to write, and every real vote write routes through
`purge_and_write_votes` (13 call sites checked). The only direct
`bulk_create` on a vote model, in
`MPCAutofill/cardpicker/harvest_probe.py`, is inside a savepoint that is
always rolled back. So v1 and v2 cannot coexist on a card.

Residual, trivial: a card v2 never revisits keeps its v1 row. Measured
exposure — `stage-d-illustration-v1` has exactly **1** remaining row
while production casts `stage-d-illustration-v2`. Not worth acting on.

#### F3 — `compute_covered_printing_pks` is not self-referential today

`MPCAutofill/cardpicker/local_identify_printing_tags.py`. Arm 1
(`canonical_card`) is written in exactly one place —
`MPCAutofill/cardpicker/sources/update_database.py`, at ingest, from the
source file's own filename tags. **No calculator writes it.** Arm 2 is
gated on `RESOLVED`, which requires a human-backed vote, so no volume of
calculator votes can add a pk unaided.

Measured composition: **10,337** covered printings, of which
`via_confirmed` = 10,337 and `via_resolved_inference` = 4 — and all four
were already in `via_confirmed`. **Net pipeline contribution: zero pks.**
Recomputed fresh on every call; no `lru_cache`, no module global, no
per-run memo; order of execution cannot change the answer.

#### F4 — `printing_tag_status=UNRESOLVED` as an eligibility filter is legitimate

It is written in exactly one place
(`MPCAutofill/cardpicker/printing_consensus.py`) and can only _leave_
`UNRESOLVED` on human input, because of the hard human-backed gate. So it
means "no human has settled this card" — an externally-driven fact
wearing a pipeline-written field's clothes. (The ratchet in `K10` is a
separate concern.)

#### F5 — `evidence_transfer` does not double-count

Verified rather than accepted from the module's own claim:
`ImageEvidence` holds **observations only** — no verdict, no
`inferred_canonical_card`, no vote outcome
(`MPCAutofill/cardpicker/models.py` walked). The retired `transferred`
Stage D guard is genuinely replaced, and the preconditions line up
exactly: `dedupe_key` is set only when the md5 group has >1 member, and
transfer only happens within an md5 group of >1. Whenever transfer
occurred, pooling is necessarily active. The printing double-count hole
**is** closed. (`K6` is a reporting spillover, not a tally error.)

#### F6 — The audit's own false alarm, corrected before reporting

Preserved verbatim in substance, because it is evidence the audit was
honest about its own method.

A first pass showed **127 "conflicts"** between `stage-d-join-key-v1` and
`local-ocr-v1`, which appeared to refute the known "33,622 / 33,622, zero
conflicts" figure. Re-run **per card, distinguishing abstention from
contradiction**, the original figure is **correct**. The 127 are cards
where join-key abstained (`is_no_match`) and OCR named a printing. Zero
cards have the two channels naming _different_ printings.

**And the corrected number is a stronger argument than the original one.**
Of 33,749 cards both channels voted on, 33,622 had both name a printing
and they **never differed**; the 127 disagreements are strictly
one-directional (join-key abstains where OCR commits; OCR never abstains
where join-key commits). That is the signature of a **strict subset** —
join-key is `local-ocr`'s decode plus extra veto layers — not of an
independent method. This is the second tell in shape 4, and it is why
one-directional containment belongs in the review checklist.

#### F7 — Also checked and clean

`pool_group_votes`/`resolve_weighted_consensus` share arithmetic that
runs entirely post-pooling; `md5_backfill`'s `dupe_factor` is
files-over-files; `MPCAutofill/cardpicker/process_metrics.py` reads
`VmRSS` from `/proc` and is **the one measurement in this audit fully
external to the pipeline**; illustration write-in vote fan-out
(`MPCAutofill/cardpicker/illustration_vote.py`) is bounded and auditable;
`question_feed._served_mix_ratio` is a feedback controller regulating its
own output, not a correctness claim, and explicitly refuses to game its
own metric.

A companion read-only audit ran on the same day against the same
production commit, asking a narrower question: does
[`../pipeline-fidelity-gate.md`](../pipeline-fidelity-gate.md)'s
certification still hold? Its verdict — "FIRED, but qualified to the

**They are deliberately separate documents.** The fidelity-gate recheck

findable by someone who has never heard of issue #154.

They meet at exactly one substantive point, and it is shape 4. The
recheck found that the gate's **83.2% "cross-method verdict diff"** is

same thing twice by different methods — which, unlike the agreement rate
either one is examining, is genuine corroboration.

## How to use this when reviewing a diff

Five questions, in the order they are cheapest to answer:

1. **Where did this expected value come from?** If the answer is "a run
   of the code under test", it is a regression snapshot, and it must not
   be called ground truth.
2. **Is there a single-line change to the implementation that would
   redden this test?** If not, the test is documentation. Say so in its
   docstring rather than counting it as coverage.
3. **What does this check print when it examined nothing?** If that is
   the same string it prints on success, fix the check before shipping
   it.
4. **Does this queryset filter on something the pipeline wrote?** If it
   is used as a denominator, a frequency, or a uniqueness test, the
   filter is part of the claim and belongs in the caption.
5. **Do these two channels share a constant?** If they share a crop box,
   a regex, a normaliser or an index, their agreement rate is not
   evidence. Check whether their disagreements are one-directional.
